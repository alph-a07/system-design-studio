HTTP/1.1 vs HTTP/2 vs HTTP/3: Where Head-of-Line Blocking Relocated

How fixing a bottleneck at the application layer exposed a deeper bottleneck at the transport layer, and why modern web architecture had to rewrite 40 years of networking stack.

01

The Causal Chain: How One Fix Bounded the Next

Unbroken Lineage from Topic 1.1

In Topic 1.1, we established that TCP treats data as a strictly ordered byte stream: if one packet is dropped, the receiver kernel halts delivery of all subsequent bytes.

Now observe what happened as application developers tried to build rich web apps on top of that byte stream. The history of HTTP protocols is not a story of adding arbitrary features; it is the story of Head-of-Line (HOL) blocking migrating up and down the network stack.

02

The Three Protocol Eras: Where Did the Jam Occur?

HTTP/1.1 (1997)

Application-Layer HOL Blocking

HTTP/1.1 transfers plain text. Only one request/response could occupy a TCP connection at a time. If image hero.jpg took 500ms to generate on the server, all other asset requests behind it were completely stuck.

Workaround: Browsers opened 6 parallel TCP sockets per domain. Expensive handshakes and cellular memory overhead!
HTTP/2 (2015)

Transport-Layer Cross-Stream Blocking

HTTP/2 introduced binary framing. Hundreds of requests could be multiplexed over a single TCP connection as independent logical "streams".

The Hidden Trap: TCP knows nothing about HTTP/2 streams! If a packet carrying 1 byte of Stream #1 drops, the TCP kernel halts the socket buffer. Streams #2 through #50 are completely blocked in kernel memory!
HTTP/3 + QUIC (2022)

True Independent Stream Isolation

QUIC abandons TCP and builds transport directly over UDP. It implements congestion control, loss detection, and encryption in user space.

The Triumph: Each stream has its own independent sequence space. If Stream #1 loses a packet, Streams #2 and #3 proceed instantly with zero stall!
